# Tross LinkedIn Profile API - API Contract

Status: canonical API design, pre-implementation
Last verified: 2026-08-31

This document defines the public HTTP contract. The response schema is owned by
this service and remains stable even when LinkedIn's upstream shape changes.

## Base URL

Local development:

```text
http://localhost:8000
```

Production:

```text
https://<railway-public-domain>
```

## Authentication

Protected endpoints require:

```text
x-api-key: <api key>
```

Rules:

- Missing or invalid keys return `401` RFC 9457 Problem Details.
- `403` is reserved for future valid-but-insufficient authorization.
- API keys are not accepted in query parameters.
- API keys are never logged.
- Accepted API keys are generated with high entropy; the service stores
  SHA-256 or HMAC digests, not raw evaluator keys.
- The evaluator API key is delivered privately and never committed.
- Health endpoints do not require an API key.

## Endpoints

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/health/live` | no | Process liveness. |
| `GET` | `/health/ready` | no | Dependency readiness for deployment. |
| `POST` | `/v1/profiles:resolve` | yes | Resolve a LinkedIn profile URL into structured JSON. |
| `GET` | `/openapi.json` | no | OpenAPI schema generated by FastAPI. |
| `GET` | `/docs` | no or environment-gated | Interactive docs in non-production or evaluator-friendly mode. |

## `POST /v1/profiles:resolve`

Request headers:

```text
content-type: application/json
x-api-key: <api key>
```

Request body:

```json
{
  "profile_url": "https://www.linkedin.com/in/example-person/"
}
```

Request schema:

```text
ResolveProfileRequest
  profile_url: string
```

Validation:

- `profile_url` must be an `http` or `https` LinkedIn public profile URL.
- Accepted hosts are `linkedin.com`, `www.linkedin.com`, and documented
  two-letter country subdomains such as `ca.linkedin.com`.
- Accepted path is `/in/{slug}` with an optional language suffix.
- Query strings and fragments are discarded.
- The original URL is never fetched.

Profile schema requirements:

- `profile.name` is required and non-empty for any `200` response.
- Profile date fields use `PartialDate`: `YYYY`, `YYYY-MM`, or `YYYY-MM-DD`.
- Operational timestamps such as `fetched_at`, `cache.stored_at`, and
  `cache.expires_at` use RFC 3339 datetimes.
- `sections` is a fixed typed object with `identity`, `about`, `experience`,
  `education`, `skills`, `certifications`, `languages`, and `images`.
- `cache` contains timestamps only. Hit/miss status is exposed through the
  `x-cache` response header.

### Partial Success Semantics

The service returns `200 OK` when it can produce a trustworthy
`ProfileResponseV1` with non-empty core identity for the requested profile,
even if some optional sections are unavailable, empty, or partially parsed.

Clients must inspect:

- `sections.<section>.status`
- `sections.<section>.item_count`
- `warnings`

Section statuses:

| Status | Meaning |
| --- | --- |
| `complete` | Section was available and parsed cleanly. |
| `partial` | Some data was parsed but one or more fields/items were unavailable or failed parsing. |
| `empty` | Upstream indicated no visible items or the section was absent in a non-error way. |
| `unavailable` | The section could not be fetched or was hidden/unsupported. |
| `parse_error` | The parser detected drift for that section but core profile data was still usable. |

Warnings:

| Code | Meaning |
| --- | --- |
| `section_unavailable` | Optional section was missing or hidden. |
| `section_parse_error` | Section-level parser failed without failing the full profile. |
| `profile_visibility_limited` | The profile appears to expose limited information. |
| `image_unavailable` | Profile/background image was not available. |
| `schema_drift_detected` | Upstream shape changed but response was still generated. |

A visibility-limited profile with usable identity is returned as partial `200`.
Negative cache is only allowed after Spike 0 proves a deterministic not-found
signal; generic `404` before Spike 0 is not treated as safely cacheable.

## Error Format

All non-2xx responses use Problem Details for HTTP APIs, RFC 9457.

Content type:

```text
application/problem+json
```

Shape:

```json
{
  "type": "https://<public-base-url>/problems/invalid-profile-url",
  "title": "Invalid LinkedIn profile URL",
  "status": 422,
  "detail": "The URL must be a LinkedIn public profile URL under /in/{slug}.",
  "instance": "/v1/profiles:resolve/req_01j...",
  "request_id": "req_01j...",
  "code": "invalid_profile_url"
}
```

Do not include:

- Raw upstream response bodies.
- Cookies or session values.
- API keys.
- Stack traces.
- Internal Redis connection strings.

## Status Codes

| Status | Code | When |
| --- | --- | --- |
| `200` | `ok` | Profile response produced. May include partial sections. |
| `400` | `invalid_json` | Request body is malformed JSON. |
| `401` | `api_key_missing` | `x-api-key` header is missing. |
| `401` | `api_key_invalid` | API key is present but invalid. |
| `403` | `insufficient_authorization` | Reserved for future valid keys that lack required authorization. |
| `422` | `invalid_profile_url` | URL fails strict canonicalization. |
| `429` | `rate_limited` | Client API key exceeds inbound limiter. |
| `503` | `upstream_budget_exhausted` | Global upstream budget is exhausted; response includes `Retry-After`. |
| `404` | `profile_not_found` | Spike-0-verified deterministic not-found and no usable identity is available. |
| `502` | `upstream_bad_response` | Upstream returned malformed/unusable data. |
| `503` | `redis_unavailable` | Redis is unavailable, so protected endpoint fails closed. |
| `503` | `upstream_cooldown_active` | Explicit upstream cooldown is active; response includes `Retry-After`. |
| `503` | `linkedin_rate_limited` | LinkedIn returned `429`; service set bounded cooldown without another LinkedIn attempt. |
| `503` | `linkedin_auth_required` | Backend LinkedIn session is invalid or logged out. |
| `503` | `linkedin_challenge_required` | LinkedIn returned challenge/checkpoint/CAPTCHA. |
| `503` | `profile_fetch_in_progress` | Single-flight wait expired and cache is still empty. |
| `504` | `upstream_timeout` | Bounded upstream operation timed out. |
| `500` | `internal_error` | Unexpected service bug. |

## Rate Limit Headers

For inbound client rate limiting:

```text
x-ratelimit-limit: <capacity>
x-ratelimit-remaining: <remaining tokens rounded down>
x-ratelimit-reset: <unix timestamp seconds>
retry-after: <seconds, only when denied>
```

For upstream protection errors:

```text
retry-after: <seconds when known>
```

Do not expose LinkedIn-specific internal headers directly.

## Health Responses

### `GET /health/live`

Success:

```json
{
  "status": "live",
  "service": "tross-linkedin-profile-api"
}
```

Failure:

- Usually only fails if the process cannot serve HTTP at all.
- Does not check Redis or LinkedIn.

### `GET /health/ready`

Success:

```json
{
  "status": "ready",
  "checks": {
    "settings": "ok",
    "redis": "ok",
    "http_client": "ok",
    "rate_limiter": "ok"
  }
}
```

Failure:

```json
{
  "status": "not_ready",
  "checks": {
    "settings": "ok",
    "redis": "failed",
    "http_client": "ok",
    "rate_limiter": "unknown"
  }
}
```

Status:

```text
503 Service Unavailable
```

Readiness does not call LinkedIn.

## OpenAPI

FastAPI generates OpenAPI from route declarations and Pydantic models.

Design requirements:

- `ProfileResponseV1` appears as the `200` response schema.
- Problem Details appears as the error response schema.
- `x-api-key` is declared as an API key security scheme.
- Examples include successful, partial, and error responses.

## Compatibility Policy

For `v1`:

- Do not remove or rename fields.
- Do not change scalar types.
- New fields require a future version or a carefully documented additive change.
- Upstream LinkedIn drift must be absorbed inside parser/domain layers whenever
  possible.

Versioning:

- Public endpoint path remains `/v1/...`.
- A future incompatible schema would be `/v2/profiles:resolve`.
